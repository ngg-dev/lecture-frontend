# Лабораторная работа 7

## Типизация проекта на TypeScript

Продолжите **свой проект из лабораторной №6**: тот же стек, те же страницы, тот же выбор
объектов и загрузка данных. Задача — перевести проект на TypeScript так, чтобы типы
описывали реальные данные, а не мешали работать. Книжный магазин из лекции — пример;
используйте свою предметную область: товары, фильмы, задачи, рецепты.

**Основной стек:** React + TypeScript, `@types/react`, `tsc --noEmit` в проверке.

Установка: `npm install -D typescript @types/react @types/react-dom`.
Файлы с JSX переименуйте в `.tsx`, добавьте `tsconfig.json` и скрипт `npm run typecheck`.

Срок сдачи назначает преподаватель. Критерии накопительные: оценка 4 включает все условия
на 3, оценка 5 — все условия на 4. Список того, что **не** считается выполнением, — в конце.

## Удовлетворительно — 3

- **Модель данных описана типами.** Для основной сущности есть `type` или `interface`
  с полями вашего домена (например `id: string`, `title: string`, `price: number`).
  Массив данных в состоянии и в props компонентов типизирован этим типом, а не `any[]`.
- **Props и callbacks.** У компонентов карточки и списка описаны props, у обработчиков —
  параметры и возвращаемое значение. Обработчик добавления имеет вид
  `(id: string) => void` или аналогичный по смыслу.
- **Состояние.** `useState` типизирован там, где вывод неочевиден: список —
  `useState<Book[]>([])`, выбранный объект — `useState<Book | null>(null)`.
  Простой счётчик остаётся без явного типа.
- **Форма.** Черновик поля ввода хранится строкой, обработчик изменения типизирован
  через `ChangeEvent<HTMLInputElement>`, при сохранении строка преобразуется в число
  с проверкой на конечность и неотрицательность.
- **Проверка проходит.** `npm run typecheck` (`tsc --noEmit`) завершается без ошибок.
  В проекте нет `any`, `@ts-ignore` и `as unknown as` в местах, которые студент
  не может объяснить.

**На защите:** покажите типы модели, props карточки и обработчик добавления.
Объясните, почему строковая цена в объекте — ошибка компилятора и что именно
проверил TypeScript. Покажите одну намеренную ошибку и её сообщение.

## Хорошо — 4

Выполнены все условия на 3, а также:

- **Утилиты типов на своём домене.** `Pick` для короткой карточки, `Omit` для данных
  новой сущности без `id`, `Record<string, number>` для выбора/корзины со значениями
  по умолчанию через `?? 0`.
- **Union для состояний.** Состояние загрузки описано объединением
  (`'idle' | 'loading' | 'success' | 'error'`) и разбирается через `typeof`/сравнение,
  а не строкой без проверки. Отдельно описан случай «успех, но список пуст».
- **Осознанный выбор `type` и `interface`.** В коде видно, почему выбран каждый:
  `interface` — когда контракт расширяется (`extends`), `type` — для объединений,
  утилит и кортежей. Расширение через `&` и `extends` использовано по назначению.
- **null-безопасность.** Перед чтением полей выбранного объекта есть проверка на `null`;
  проект собирается со `strict: true`, `strictNullChecks` не отключён.
- **Внешние данные.** Ответ запроса типизирован, и тип не выдан за проверку:
  данные из `fetch`/JSON принимаются как `unknown` и проверяются перед использованием
  (guard-функция или явная проверка полей). `as Book[]` без проверки — не считается.
- **Скрипты проекта.** `typecheck` добавлен в `package.json` и выполняется в том же
  наборе команд, что и сборка. В README проекта указано, как запустить проверку.

**На защите:** покажите карточку `Pick`, объект `Omit`, `Record` выбора и откуда
берётся `?? 0`. Переключите состояние загрузки и покажите, что все ветки union
обработаны. Покажите, что произойдёт, если API вернёт поле не того типа.

## Отлично — 5

Выполнены все условия на 4, а также:

- **Свой generic.** Написана хотя бы одна функция или хук с параметром типа, полезные
  в проекте: например `toArray<T>(value: T | T[]): T[]` или
  `useLocalStorage<T>(key: string, initial: T)`. Generic не декоративный: без него
  пришлось бы дублировать код или терять тип.
- **Типизированные API и асинхронность.** Функция запроса возвращает `Promise<Book[]>`
  (или `Promise<Book>`), ошибка обрабатывается с типом, а не глушится `catch (e) {}`.
  Результат запроса попадает в состояние с явным типом, без `any` на границе.
- **Ни одного «обхода» типов.** В проекте нет `@ts-ignore`, `@ts-expect-error`
  без объяснения причины, `any` и слепых `as`.

**На защите:** покажите свой generic и объясните, что выведется при разных аргументах. Продемонстрируйте проверку внешних данных на «плохом» ответе и объясните, что было бы при `as`.

## Что не считается выполнением

- `any` вместо типа, `@ts-ignore` над ошибкой, `as unknown as T` без объяснения.
- Отключённые `strict`/`strictNullChecks`, «временно» выключенная проверка в скрипте.
- Типы, описанные, но не связанные с данными: `interface Book` есть, а в состоянии
  и props по-прежнему `any[]`.
- Проверка, которая проходит только на неполном коде: проект не собирается или
  интерфейс перестал работать после типизации.
- Переписывание проекта с нуля вместо типизации своего: лабораторная продолжает №6.

## Что сдать

1. Ссылка на репозиторий (или PR) с проектом, продолжающим лабораторную №6.
2. `tsconfig.json` и скрипт `typecheck` в `package.json`.
3. Короткая записка на 5–7 строк: какая сущность типизирована, какие утилиты типов
   использованы, где пришлось проверять внешние данные и что осталось нетипизированным
   осознанно.
4. Лог `npm run typecheck` без ошибок.

## Как проверять (для проверяющего)

1. Склонировать, `npm ci`, `npm run typecheck` — должно пройти без ошибок и без
   подавлений (`grep -R "@ts-ignore\|: any\|as unknown as" src`).
2. Открыть модель данных и карточку: совпадают ли типы с реальными полями и props.
3. Проверить «три уровня» по таблице ниже; каждый следующий включает предыдущий.
4. На защите задать 3 вопроса из своего уровня и один «а если данные придут другие».

| Оценка | Что должно быть видно в коде | Что спрашивать |
| --- | --- | --- |
| 3 | типы модели, props, состояние, `tsc` без ошибок, без `any` | «почему строковая цена — ошибка», «что типизирует `useState<Book[]>`» |
| 4 | `Pick`/`Omit`/`Record`, union состояний, `strict`, проверка внешних данных | «почему тут `type`, а там `interface`», «что будет с `null` при чтении полей» |
| 5 | свой generic, `Promise<T>` с типизированной ошибкой | «что выведет generic при другом аргументе», «почему ошибка обрабатывается с типом, а не глушится» |
