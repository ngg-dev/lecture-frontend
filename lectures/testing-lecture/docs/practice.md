# Практика: регрессия больше не проходит незамеченной

**20 минут: unit 6, компонент 6, браузер 8.** Продолжайте свой React/TypeScript-проект с предыдущих занятий. Не переписывайте его и не заменяйте готовым книжным магазином. Для другого предмета используйте свою сущность и аналогичное правило ввода.

## Что уже есть

Форма меняет числовое поле сущности, карточка показывает его, действие добавляет сущность в список/корзину. Вы знаете props, события, состояние и async/await. Если в проекте нет корзины, возьмите другой сквозной путь: создать элемент → увидеть его в списке.

## 1. Правило — 6 минут

Проблема: пустая строка после `Number` стала нулём, хотя пустоту нужно отклонять.

1. Выберите или вынесите чистую функцию преобразования: строка → число либо отказ.
2. Опишите бизнес-правило словами. Решите отдельно, допустим ли ноль.
3. Добавьте Vitest. Напишите тест пустого ввода и запустите на ошибочной версии. Он должен упасть именно на ожидании, не на импорте.
4. Исправьте функцию. Добавьте корректный ввод, пустоту/пробелы, минус, нечисловое значение и границу ноль.
5. Запустите все тесты. Не вычисляйте ожидаемое значение той же функцией, которую проверяете.

**Проверяемый результат:** до исправления есть красный тест, после — зелёный набор; `Number('')` больше не выдаётся за корректную цену.

Слайды: «Сначала определим, что считается правильным», «Один тест — три части», «Красный тест должен падать по нужной причине», «Один happy path оставляет дыру».

## 2. Компонент — 6 минут

Проблема: функция работает, но форма может не вызвать callback или передать неверное значение.

1. Настройте Vitest + jsdom, React Testing Library, user-event и jest-dom. Очистите DOM после каждого теста.
2. Отрендерите существующий компонент с контролируемым callback. Сам компонент и функцию не подменяйте.
3. Найдите поле по роли/label, очистите его, введите корректное значение, нажмите сохранение. Проверьте числовой аргумент callback и видимое подтверждение, если оно предусмотрено вашим интерфейсом.
4. Отдельно отправьте пустое поле: виден отказ, callback не вызван.
5. Если сохранение асинхронное, задайте rejected Promise: пользователь видит ошибку и может повторить. Ждите DOM через findBy или waitFor, не через sleep.

**Проверяемый результат:** взаимодействие проходит, пустое значение не отправляется. Тест не зависит от имени useState-переменной, CSS-класса или числа render-вызовов.

Слайды: «Кликаем так, как кликает пользователь», «Как выбрать правильный элемент?», «Сохранение не заканчивается мгновенно», «Как проверить ошибку, не ломая настоящий сервер?».

## 3. Браузер — 8 минут

Проблема: отдельные части зелёные, но целый путь пользователя сломан.

1. Установите Playwright и Chromium. Соберите проект и запустите его HTTP-сервер.
2. В новом тесте откройте страницу и выполните один критический путь через роли и доступные имена.
3. Проверьте конечный результат: элемент виден в корзине/списке и итог/состояние соответствует действию.
4. Каждый тест сам готовит данные. Не используйте результат другого теста.
5. Если API внешний или стенд недоступен, перехватите его до перехода. Подпишите: это тест фронтенда с mock API, а не проверка backend.
6. Уберите обработчик действия: тест должен упасть. Верните его и добейтесь зелёного запуска.

**Проверяемый результат:** настоящий браузер проходит собранный проект; нет `waitForTimeout`, `force: true`, `skip` и проглатывания ошибок.

Слайды: «Где заканчивается наш e2e?», «Книга должна попасть в корзину», «Почему не нужен waitForTimeout?», «Тест не должен зависеть от предыдущего».

## Защита результата

Покажите:
- команду одного запуска тестов с корректным exit code;
- намеренную поломку, которая делает нужный тест красным, и исправление;
- какой риск ловит каждый из трёх уровней;
- какую часть системы ваш mock исключил из проверки.

Не считается результатом: тест без assertion; ожидание только `toBeDefined`; подмена тестируемой функции; snapshot всей страницы без осмысленной проверки; тест зелёный при удалённом действии; скопированный магазин вместо продолжения проекта.
