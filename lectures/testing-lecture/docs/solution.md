# Сверка после самостоятельной попытки

Материал для сверки после необязательной 20-минутной практики, которая идёт отдельно от 70-минутной лекции. Это не условие новой лабораторной и не готовый проект на замену вашему. Эталон в `packages/testing-lecture/` показывает границы проверок на знакомом магазине.

## 1. Unit

Файл `src/shop/model.ts`:

```ts
export function parsePrice(draft: string): number | null {
  if (draft.trim() === '') return null;
  const value = Number(draft);
  return Number.isFinite(value) && value >= 0 ? value : null;
}
```

`tests/model.test.ts` проверяет корректное число, пустоту, пробелы, отрицательное, NaN/Infinity и допустимый ноль. Ожидания заданы из правила. Временно замените тело на `return Number(draft)` — набор должен покраснеть. Верните исправление.

Это упрощённый учебный парсер: десятичная точка, семантика `Number`. Он не решает локализацию, валютные округления и хранение денег в production.

## 2. React-компонент

`tests/PriceEditor.test.tsx` рендерит настоящий `src/shop/PriceEditor.tsx`. Подменяется только `onSave`:

- корректный ввод передаётся числом, виден status;
- пустой ввод показывает alert, `onSave` не вызывается;
- rejected Promise показывает ошибку; повтор успешен;
- пока Promise не завершён, повторная отправка отключена.

Jest запускает unit и компонентные тесты через `babel-jest`: конфигурация в `jest.config.cjs` и `babel.config.cjs`. Babel преобразует TS/TSX, а `tsc --noEmit` отдельно проверяет типы. Тесты импортируют API из `@jest/globals`; `tests/setup.ts` подключает `@testing-library/jest-dom/jest-globals` и `afterEach(cleanup)`. `getByRole` ищет существующий элемент; `findByRole` ждёт его появления. Никакого доступа к внутреннему state.

## 3. Браузер

`e2e/shop.spec.ts` открывает настоящий собранный магазин. Базовый сценарий добавляет книгу в корзину и проверяет книгу, количество и сумму. Данные в памяти страницы, каждый тест начинает заново.

Сценарий `mode=api` регистрирует `page.route` до навигации. GET возвращает книгу, первый PATCH — HTTP 500, второй — цену 790. Он проверяет отказ, сохранение старого значения и успешный повтор. UI и fetch настоящие, HTTP-ответы контролируются тестом: backend не проверен.

Для настоящего полного e2e пришлось бы предоставить тестовый API, подготовить данные в БД и очистить их после теста. Pages — статический хостинг, поэтому реального API здесь нет.

## Команды эталона

Из `packages/testing-lecture/`:

```sh
npm ci
npm run check
```

Затем из корня репозитория в первом терминале:

```sh
npm run build
python3 -m http.server 4193 --bind 127.0.0.1 --directory ..
```

Во втором, из корня:

```sh
cd packages/testing-lecture
npx playwright install chromium
npm run test:e2e
```

Полная инструкция и смена baseURL — в README пакета. Для dev используйте `LECTURE_BASE_URL=http://127.0.0.1:4192/`, предварительно запустив `npm run dev` отдельно.

## Самопроверка

- Сначала названы риск и наблюдаемый результат, затем выбран инструмент. Unit не выдаётся за проверку браузера, а mock API — за проверку сервера.
- При удалении проверки пустоты ломается именно соответствующий unit.
- При отключении submit ломается компонентный тест.
- При отключении добавления в корзину ломается браузерный сценарий.
- После восстановления кода всё зелёное без изменения ожиданий.
- Тесты не пишут в production и не зависят от порядка.
- Вы можете назвать границу каждого теста и то, чего он не доказывает.

Если вы использовали ИИ, сравните предложенные случаи с контрактом: `''`, пробелы, минус, нечисловое и бесконечное значение должны отклоняться, `'0'` — приниматься. Черновик должен проверять настоящую функцию и содержать независимые ожидаемые значения. Тот же эксперимент с `return Number(draft)` обязан сделать тест пустоты красным. Сохраните правило и assertions при исправлении реализации; не принимайте предложенную замену ожидания на ошибочный результат.
