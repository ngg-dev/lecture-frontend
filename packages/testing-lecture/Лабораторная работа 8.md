# Лабораторная работа 8

## Unit и e2e-тестирование

Продолжите **свой проект из лабораторной №7**: та же предметная область, страницы,
загрузка данных, состояние и TypeScript. Не переписывайте приложение с нуля и не
заменяйте его готовым магазином из лекции. Добавьте проверки к работающему коду.

**Срок:** 2 недели от лекции 07.11 — до 21.11.2026.

**Стек:** Jest — unit-тесты; Playwright — браузерные сценарии. Типы по-прежнему проверяет
`tsc --noEmit`, а не Babel и не успешный запуск тестов.

Критерии накопительные: **4 включает все условия на 3; 5 включает все условия на 4**.
Проценты coverage, CI, Docker, настоящий backend и собственный test runner не требуются.

## С чего начать

1. Выберите, что важно проверить в вашем проекте: например, пустое поле не должно
   превращаться в ноль, а добавленный товар должен появляться в корзине.
2. Вынесите одно такое правило в функцию, которую можно вызвать из теста.
   Напишите в README, какие данные ей передавать и какой ответ ожидать.
3. На 4 добавьте тесты второй функции и загрузки или сохранения данных.
   На 5 проверьте важные действия пользователя в браузере.

Установка инструментов в **свой** проект:

```sh
npm install -D jest @jest/globals @types/jest \
  babel-jest @babel/core@7 @babel/preset-env@7 \
  @babel/preset-typescript@7
# Для оценки 5 дополнительно:
npm install -D @playwright/test
npx playwright install chromium
```

Добавьте `"test": "jest"` в `package.json`; для оценки 5 —
`"test:e2e": "playwright test"`. Сохраните `typecheck` и `build` из предыдущей работы.
Приложите обновлённые `package.json` и `package-lock.json`.

Для unit достаточно Node-окружения: DOM, JSX и отдельный setup-файл не нужны.
Минимальные конфигурации для TypeScript:

```js
// jest.config.cjs
module.exports = {
  testEnvironment: 'node',
  testMatch: ['<rootDir>/tests/**/*.test.ts'],
  transform: { '^.+\\.[jt]s$': 'babel-jest' },
  clearMocks: true,
  restoreMocks: true,
};
```

```js
// babel.config.cjs
module.exports = {
  presets: [
    ['@babel/preset-env', { targets: { node: 'current' }, modules: 'commonjs' }],
    '@babel/preset-typescript',
  ],
};
```

Jest ищет тесты только в `tests/`, Playwright — только в `e2e/`;
runner-ы не должны собирать чужие файлы. При `type: module` конфигурации Jest/Babel
оставьте `.cjs`. API Jest импортируйте из `@jest/globals`.
Для оценки 5 дополните конфигурацию Playwright: `testDir: './e2e'`,
`use: { trace: 'retain-on-failure' }` и
`reporter: [['list'], ['html', { open: 'never' }]]`. Сохраните свой `baseURL`
и используйте его в `page.goto`. Пример лекции включает только list-reporter:
без добавления html-reporter HTML-отчёт не появится.

## Удовлетворительно — 3

- Выберите одну функцию, которая уже используется в вашем проекте: например,
  проверку введённой цены. Напишите в README, какие данные она принимает и что
  должна возвращать.
- Напишите для неё тесты на Jest — минимум **6 разных случаев**: обычное правильное
  значение, значение на границе допустимого и четыре неправильных. Например, для цены:
  `100`, `0`, пустая строка, пробелы, `-1` и `abc`. В своём проекте используйте свои правила.
- Тесты должны вызывать настоящую функцию из `src/`, а не её копию. В каждом тесте
  заранее укажите правильный ответ и сравните его с результатом функции. Можно использовать
  `test.each`: важно проверить шесть случаев, а не создать шесть файлов.
- Хотя бы один тест разделите на три шага: **подготовить данные → вызвать функцию →
  проверить ответ**. Это подход AAA из лекции.
- Временно измените функцию так, чтобы она возвращала неправильный ответ. Убедитесь,
  что тест обнаружил ошибку. Верните правильный код — тест должен пройти.
  Сохраните вывод обоих запусков и кратко напишите, что меняли. Ошибка в синтаксисе
  или пути импорта для такой демонстрации не подходит.
- Команды `npm test`, `npm run typecheck` и `npm run build` проходят без ошибок.
  Сам проект по-прежнему работает.

**На защите:** покажите функцию и тесты, запустите их, внесите ошибку и исправьте её.
Вопросы: «Какие три шага есть в тесте?», «Откуда вы знаете правильный ответ?»,
«Может ли функция работать правильно, а кнопка на странице — нет?».

## Хорошо — 4

Выполните всё на «Удовлетворительно», а также:

- Проверьте ещё одну функцию своего проекта: например, подсчёт суммы или фильтрацию
  списка. Напишите минимум **3 случая**: обычные данные, пустые данные и значение
  на границе допустимого. Например, для количества — минимальное разрешённое число.
- Напишите тесты для своей функции загрузки или сохранения данных. Проверьте два
  варианта: **запрос выполнен успешно** и **запрос завершился ошибкой**. Проверяйте
  полученные данные или сообщение об ошибке, а не только факт вызова функции.
- В тесте можно заменить настоящий запрос заранее заданным ответом — это mock.
  Саму функцию загрузки или сохранения не подменяйте. Для подмены запроса подходят
  `jest.fn` и `jest.spyOn`.
- Дождитесь завершения запроса через `await`, `.resolves` или `.rejects`.
  Каждый тест должен сам задавать свои данные и ответ запроса. Убирайте подмены после
  тестов, чтобы они не влияли друг на друга. Не заменяйте ожидание запроса паузой.

**На защите:** покажите тесты второй функции, успешного запроса и ошибки.
Временно измените ответ функции или уберите обработку ошибки — нужный тест должен
перестать проходить. Затем верните правильный код.
Вопросы: «Что в тесте заменено заранее заданным ответом?», «Зачем нужен await?»,
«Проверили ли вы настоящий сервер, если ответ запроса подменён?».

## Отлично — 5

Выполните всё на «Хорошо», а также:

- Напишите **два теста на Playwright**, которые открывают ваш сайт по HTTP в Chromium
  и выполняют действия пользователя. Первый проверяет важное действие от начала до
  результата: например, добавить товар в корзину и увидеть правильный товар и сумму.
  Проверки одного заголовка страницы недостаточно.
- Второй тест проверяет ошибку загрузки или сохранения и повторную попытку.
  При ошибке пользователь видит сообщение, а сайт не показывает ложный успех.
  После успешного повтора данные на странице обновляются.
- Каждый тест сам готовит начальные данные и работает независимо от других тестов.
  Ответы сервера можно задавать через `page.route` до запроса. Если подменяете ответы,
  напишите об этом в README: такой тест проверяет сайт, но не настоящий сервер и БД.
  Свой сервер и БД для работы не обязательны.
- Находите кнопки и поля по их назначению и названию: например, кнопку «Сохранить» —
  через `getByRole`. Ждите нужного результата с помощью `await expect(...)`.
  Не добавляйте паузы `waitForTimeout`, принудительные клики `force: true`
  и скрытую обработку ошибок только ради прохождения теста.
- Добавьте команду `npm run test:e2e`. В README напишите, как запустить сайт для тестов
  и по какому адресу он должен работать. Можно настроить автоматический запуск
  через Playwright `webServer`.
- Временно отключите проверяемую кнопку или её действие. Тест должен обнаружить
  поломку. Верните код и убедитесь, что тест снова проходит. Сохраните вывод обоих
  запусков, HTML-отчёт и **trace — запись шагов теста при ошибке**.
  Для сохранения trace укажите `trace: 'retain-on-failure'` в настройках Playwright.

**На защите:** запустите оба теста, покажите отчёт и запись шагов при ошибке.
Покажите поломку и исправление.
Вопросы: «Что делает пользователь в этом тесте?», «Откуда берутся начальные данные?»,
«Что осталось непроверенным, если ответы сервера подменены?».

## Что не считается выполнением

- Переписанный проект, скопированный магазин лекции или тесты функций, не используемых
  в приложении. Самостоятельный пример вместо продолжения №7 не засчитывается.
- Подмена тестируемой функции/компонента, тест без assertion, `expect(true).toBe(true)`,
  только `toBeDefined` или snapshot всей страницы вместо проверки поведения.
- Ожидание, вычисляемое тем же кодом, который проверяется; изменение ожидания вместо
  исправления реальной ошибки; тест остаётся зелёным после поломки проверяемого действия.
- `skip`, `todo`, `only`, отключённые тесты, `--passWithNoTests`, `--forceExit`,
  проглоченные ошибки, произвольные паузы или принудительные клики для обхода причины падения.
- Отключение TypeScript-проверки, ослабление `strict`, новые `any`, `@ts-ignore` или
  необъяснённые приведения для обхода ошибок. Успех Babel не заменяет `tsc --noEmit`.
- Скриншот зелёного вывода без исполнимых тестов. Число тестов и процент coverage сами
  по себе не заменяют требуемые сценарии.

ИИ можно использовать для предложения случаев и черновика тестов. Ответственность
за контракт, ожидания, запуск и демонстрацию регрессии остаётся у студента.

## Что сдать

1. Ссылку на репозиторий или PR — продолжение №7; исходники, тесты, конфиги и lockfile.
2. README с контрактом, командами запуска, границами mock и пояснением рисков на 5–7 строк.
3. Вывод зелёных `npm test`, `npm run typecheck`, `npm run build` и пару «красный/зелёный»
   для unit с описанием внесённой поломки.
4. На 5 дополнительно: вывод `npm run test:e2e`, HTML-отчёт, trace падения и пару
   «красный/зелёный» для браузерного сценария. Артефакты можно передать архивом:
   секреты, `.env`, `node_modules` и личные данные в него не включать.

## Как проверять (для проверяющего)

Все команды выполняются **в репозитории студента**, а не в пакете примеров лекции.

```sh
npm ci
npm run typecheck
npm test -- --runInBand
npm run build
# Для оценки 5:
npx playwright install chromium
# Если webServer не настроен, сначала запустите приложение
# отдельной командой и на порту из README студента.
npm run test:e2e
npx playwright show-report
npx playwright show-trace <путь-к-trace.zip>
```

Сделайте повторный запуск на исправленной версии. Изучите конфиги: Jest не собирает
`e2e/`, Playwright не собирает `tests/`; TypeScript-проверка не отключена. Перед сценарием
отказа не нужно ломать настоящий сервис — достаточно управляемого mock.

Поиск потенциальных обходов (совпадение — повод прочитать строку, а не автоматический отказ):

```sh
grep -RInE '(test|it|describe)\.(skip|only|todo)|waitForTimeout|force:[[:space:]]*true|@ts-ignore|as unknown as|:[[:space:]]*any' src tests e2e
grep -nE 'passWithNoTests|forceExit|strict.*false' package.json tsconfig*.json
```

На 3/4 папки `e2e/` может ещё не быть: исключите её из первой команды.
Проверьте `.catch`, mock-реализации и ожидания вручную; grep не доказывает отсутствие обходов.

| Оценка | Что должно быть видно в коде | Что показать и спросить |
| --- | --- | --- |
| 3 | Одна функция проекта, описание её работы, ≥6 случаев, три шага AAA, успешные проверки типов и сборка | Внесите ошибку и исправьте; что тест не проверяет на странице? |
| 4 | Всё на 3; вторая функция (≥3 случая), загрузка/сохранение: успех и ошибка, подмены не влияют на другие тесты | Что заменили в тесте, зачем нужен await, проверили ли настоящий сервер? |
| 5 | Всё на 4; два теста в браузере, свои данные у каждого теста, отчёт и запись шагов | Покажите поломку и исправление; что не проверено при подмене ответов сервера? |

Итог — максимальный уровень, для которого выполнены **все** условия, включая предыдущие.
