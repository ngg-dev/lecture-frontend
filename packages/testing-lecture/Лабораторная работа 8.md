# Лабораторная работа 8

## Unit и e2e-тестирование

Продолжите **свой проект из лабораторной №7**: та же предметная область, страницы,
загрузка данных, состояние и TypeScript. Не переписывайте приложение с нуля и не
заменяйте его готовым магазином из лекции. Добавьте проверки к работающему коду.

**Срок:** 2 недели от лекции 07.11 — до 21.11.2026.

**Стек:** Jest — unit-тесты; Playwright — браузерные сценарии. Типы по-прежнему проверяет
`tsc --noEmit`, а не Babel и не успешный запуск тестов.

Критерии накопительные: **4 включает все условия на 3; 5 включает все условия на 4**.
Проценты coverage, CI, Docker, настоящий backend и собственный test runner не требуются.

## С чего начать

1. Выберите обещание существующего проекта и конкретный риск для пользователя:
   например, пустое поле превращается в ноль, изменение не сохраняется или выбранный
   объект не появляется в общем списке. Сначала сформулируйте правильное поведение.
2. Для unit выделите из существующего кода одно правило в импортируемую функцию.
   В README проекта опишите входы и ожидаемые результаты, включая ошибочные и граничные.
3. На 4 добавьте проверки второго правила и асинхронной функции своего проекта.
   На 5 проверьте критический путь через интерфейс в браузере.

Установка инструментов в **свой** проект:

```sh
npm install -D jest @jest/globals @types/jest \
  babel-jest @babel/core@7 @babel/preset-env@7 \
  @babel/preset-typescript@7
# Для оценки 5 дополнительно:
npm install -D @playwright/test
npx playwright install chromium
```

Добавьте `"test": "jest"` в `package.json`; для оценки 5 —
`"test:e2e": "playwright test"`. Сохраните `typecheck` и `build` из предыдущей работы.
Приложите обновлённые `package.json` и `package-lock.json`.

Для unit достаточно Node-окружения: DOM, JSX и отдельный setup-файл не нужны.
Минимальные конфигурации для TypeScript:

```js
// jest.config.cjs
module.exports = {
  testEnvironment: 'node',
  testMatch: ['<rootDir>/tests/**/*.test.ts'],
  transform: { '^.+\\.[jt]s$': 'babel-jest' },
  clearMocks: true,
  restoreMocks: true,
};
```

```js
// babel.config.cjs
module.exports = {
  presets: [
    ['@babel/preset-env', { targets: { node: 'current' }, modules: 'commonjs' }],
    '@babel/preset-typescript',
  ],
};
```

Jest ищет тесты только в `tests/`, Playwright — только в `e2e/`;
runner-ы не должны собирать чужие файлы. При `type: module` конфигурации Jest/Babel
оставьте `.cjs`. API Jest импортируйте из `@jest/globals`.
Для оценки 5 дополните конфигурацию Playwright: `testDir: './e2e'`,
`use: { trace: 'retain-on-failure' }` и
`reporter: [['list'], ['html', { open: 'never' }]]`. Сохраните свой `baseURL`
и используйте его в `page.goto`. Пример лекции включает только list-reporter:
без добавления html-reporter HTML-отчёт не появится.

## Удовлетворительно — 3

- **Контракт своего правила.** В README перечислены минимум шесть разных случаев:
  обычный корректный, граничный корректный и минимум четыре ошибочных. Для проверки
  числового поля подходят положительное значение, ноль, пустота, пробелы, отрицательное
  и нечисловой ввод. Для другого правила выберите аналогичные риски своего домена;
  границу определяет контракт проекта, а не пример магазина.
- **Работающие unit-тесты.** Jest проверяет все перечисленные случаи настоящей функции,
  импортированной из `src/`. `test.each` допустим: считаются проверяемые случаи, а не
  число файлов или вызовов `test`. У каждого случая есть проверка конкретного результата;
  ожидаемое значение не вычисляется тестируемой функцией.
- **AAA.** Хотя бы один тест явно разделён на Arrange, Act и Assert. На защите студент
  показывает подготовку входа, вызов и проверку результата; комментарии без этих действий
  не засчитываются.
- **Полезность доказана.** Временно внесите одну логическую ошибку в рабочую функцию:
  подходящий тест падает на неверном результате, а не на синтаксисе или импорте.
  Восстановите код — тот же тест проходит. Сохраните вывод обоих запусков и описание
  изменения; сдаваемая версия должна быть исправлена.
- **Проверки запускаются.** `npm test`, `npm run typecheck` и `npm run build`
  завершаются без ошибок. Типизация и поведение проекта из №7 сохранены.

**На защите:** покажите контракт и тесты, выполните один запуск, внесите и отмените
намеренную ошибку. Вопросы: «Где в этом тесте AAA?», «Почему ожидаемое значение известно
независимо от реализации?», «Какую поломку интерфейса unit не заметит?».

## Хорошо — 4

Выполнены все условия на 3, а также:

- **Второе правило проекта.** Jest проверяет ещё одну настоящую функцию из `src/`:
  например, подсчёт итога, изменение количества или фильтрацию. Есть минимум три разных
  случая: обычный результат, пустые данные и граничное значение по контракту.
- **Асинхронность.** Для своей функции загрузки или сохранения проверены успешный ответ
  и ошибка. Используйте `async/await`, `.resolves` или `.rejects` по контракту функции;
  проверяйте возвращаемые данные или ошибку, а не только факт вызова.
- **Mock только на внешней границе.** Запрос или переданный API-клиент можно подменить
  через `jest.fn`/`jest.spyOn`, саму проверяемую функцию — нельзя. В каждом тесте заново
  задаются ответы и исходные данные, spies восстанавливаются; произвольных пауз нет.

**На защите:** покажите второе правило, успешный запрос и отказ. Временно уберите
обработку ошибки или исказите результат — соответствующий тест должен упасть.
Вопросы: «Что именно подменил mock?», «Почему нужно ждать Promise?»,
«Доказывает ли этот тест работоспособность настоящего сервера?».

## Отлично — 5

Выполнены все условия на 4, а также:

- **Два браузерных сценария.** Playwright открывает свой проект по HTTP в Chromium.
  Первый проходит критический успешный путь, например добавление объекта в выбор/корзину
  с проверкой состава и итога. Второй проверяет отказ загрузки или сохранения и успешный
  повтор: видна ошибка, неверный успех не показан, после повтора интерфейс обновлён.
  Одна проверка заголовка страницы не является критическим путём.
- **Управляемые данные.** Каждый тест сам подготавливает исходное состояние; результат
  не зависит от порядка запусков или данных другого теста. Для сценария отказа можно
  перехватить HTTP через `page.route` до действия/перехода. В README явно укажите, где mock
  и что backend при таком запуске не проверяется. Реальный сервер и БД не обязательны.
- **Устойчивые ожидания.** Используйте роли/доступные имена и ожидаемые проверки
  Playwright. Нет `waitForTimeout`, `force: true` и проглатывания ошибок ради зелёного
  результата. `test:e2e` запускается одной командой; адрес, порт и подготовка сервера
  описаны в README. Можно настроить Playwright `webServer` для автоматического старта.
- **Браузерный тест ловит регрессию.** Временно отключите обработчик критического действия:
  соответствующий сценарий падает на проверке результата. Верните код и повторите запуск.
  Приложите вывод красного и зелёного запусков, HTML-отчёт и trace падения.
  Настройте `trace: 'retain-on-failure'`; trace создаётся на настоящем падении.

**На защите:** запустите оба сценария, откройте отчёт и trace. Покажите намеренную
поломку и восстановление. Вопросы: «Какая часть системы действительно проверена?»,
«Как тест задаёт исходные данные?», «Почему зелёный тест с mock API не доказывает работу БД?».

## Что не считается выполнением

- Переписанный проект, скопированный магазин лекции или тесты функций, не используемых
  в приложении. Самостоятельный пример вместо продолжения №7 не засчитывается.
- Подмена тестируемой функции/компонента, тест без assertion, `expect(true).toBe(true)`,
  только `toBeDefined` или snapshot всей страницы вместо проверки поведения.
- Ожидание, вычисляемое тем же кодом, который проверяется; изменение ожидания вместо
  исправления реальной ошибки; тест остаётся зелёным после поломки проверяемого действия.
- `skip`, `todo`, `only`, отключённые тесты, `--passWithNoTests`, `--forceExit`,
  проглоченные ошибки, произвольные паузы или принудительные клики для обхода причины падения.
- Отключение TypeScript-проверки, ослабление `strict`, новые `any`, `@ts-ignore` или
  необъяснённые приведения для обхода ошибок. Успех Babel не заменяет `tsc --noEmit`.
- Скриншот зелёного вывода без исполнимых тестов. Число тестов и процент coverage сами
  по себе не заменяют требуемые сценарии.

ИИ можно использовать для предложения случаев и черновика тестов. Ответственность
за контракт, ожидания, запуск и демонстрацию регрессии остаётся у студента.

## Как проверять (для проверяющего)

Все команды выполняются **в репозитории студента**, а не в пакете примеров лекции.

```sh
npm ci
npm run typecheck
npm test -- --runInBand
npm run build
# Для оценки 5:
npx playwright install chromium
# Если webServer не настроен, сначала запустите приложение
# отдельной командой и на порту из README студента.
npm run test:e2e
npx playwright show-report
npx playwright show-trace <путь-к-trace.zip>
```

Сделайте повторный запуск на исправленной версии. Изучите конфиги: Jest не собирает
`e2e/`, Playwright не собирает `tests/`; TypeScript-проверка не отключена. Перед сценарием
отказа не нужно ломать настоящий сервис — достаточно управляемого mock.

Поиск потенциальных обходов (совпадение — повод прочитать строку, а не автоматический отказ):

```sh
grep -RInE '(test|it|describe)\.(skip|only|todo)|waitForTimeout|force:[[:space:]]*true|@ts-ignore|as unknown as|:[[:space:]]*any' src tests e2e
grep -nE 'passWithNoTests|forceExit|strict.*false' package.json tsconfig*.json
```

На 3/4 папки `e2e/` может ещё не быть: исключите её из первой команды.
Проверьте `.catch`, mock-реализации и ожидания вручную; grep не доказывает отсутствие обходов.

| Оценка | Что должно быть видно в коде | Что показать и спросить |
| --- | --- | --- |
| 3 | Настоящая функция, контракт, ≥6 случаев с конкретными ожиданиями, AAA, проходящие типы и сборка | Красный/зелёный unit; что он не проверяет в UI? |
| 4 | Всё на 3; второе правило (≥3 случая), асинхронная функция: успех и ошибка, изолированные mocks | Что подменил mock, зачем ждать Promise, что не проверено на сервере? |
| 5 | Всё на 4; два браузерных сценария, изолированные данные, отчёт и trace | Красный/зелёный e2e; где граница фронтенда и backend? |

Итог — максимальный уровень, для которого выполнены **все** условия, включая предыдущие.
