# Заметки преподавателя

**42 слайда, 84 минуты рассказа; практика отдельно 20 минут.** Смысл редакции: реальные последствия и человеческие ожидания вместо пересказа документации. В основном показе пять фрагментов кода по 5–8 строк. Полный код и настройки остаются в README и тестовых файлах.

## Маршрут

- **Зачем проверять до релиза — 22 минуты.** Знакомый магазин, пустая цена, затем Knight Capital / GitLab / Cloudflare. После каждого случая: что потеряли, какое обещание оказалось непроверенным, какая защита нужна. Вернуться к обычным ситуациям — скидка, время записи, потерянный текст.
- **Правило, которое нельзя сломать — 19 минут.** Jest как средство, минимальный `"test": "jest"`, договорённость о цене, отдельная методология AAA, короткий тест, красный/зелёный и живой эксперимент.
- **Что видит пользователь — 15 минут.** Ложное «Сохранено», повторный клик, медленная сеть, отказ и повтор без потери ввода. Компонентный тест проверяет наблюдаемый эффект.
- **Проверяем целый путь — 14 минут.** Части работают, связи сломаны. Короткий Playwright-путь, границы mock API, непредсказуемая скорость и данные, которые надо готовить заново.
- **Выбираем полезные проверки — 14 минут.** Как начать без тестов, почему coverage не гарантия, проверка самого теста, процесс выпуска, обсуждение рисков своего проекта.

Практику можно вставить после `#practice-task` либо после рассказа. Если пара короче, сократить обсуждение исторических случаев; не расширять рассказ конфигами ради «полноты».

## Главный приём

Каждую тему читать в порядке **человек → обещание → сбой → ущерб → проверка**. Не начинать с импорта или matcher-а. Сначала попросить аудиторию назвать ожидание словами; затем показать короткий тест как запись уже понятной мысли.

## Исторические случаи: что можно и нельзя утверждать

- **Knight Capital:** SEC описала недостаточные процедуры тестирования и выкладки, слабые ограничители риска. Не говорить «тестов не было» или «unit точно спас бы $460 млн».
- **GitLab:** тестирование восстановления не имело ответственного, штатные бэкапы не работали. Это не проверка для Jest/Playwright и не потеря всех Git-репозиториев.
- **Cloudflare:** тесты были и прошли. Не оценивался чрезмерный CPU, было несколько сопутствующих причин. Не сводить вывод к «нужно больше unit».

Ссылки и точные границы — [incidents.md](incidents.md). Предлагаемые преподавателем проверки явно отделены от фактов расследований. Бытовые ситуации на слайдах названы учебными, без вымышленных названий компаний.

## До пары

1. Выполнить `npm ci`, `npm test`, `npm run check` из пакета.
2. Собрать курс из корня и поднять HTTP-сервер по README. Выполнить `npm run test:e2e` из пакета.
3. Открыть деку и обычный `shop/`. Не открывать `?mode=api` как автономное демо: API на Pages отсутствует, в тесте запросы перехватываются.
4. Проверить оглавление, прямой hash, ввод в демо и узкий экран. N открывает заметку текущего слайда.
5. Открыть полные `tests/model.test.ts`, `tests/PriceEditor.test.tsx`, `e2e/shop.spec.ts` только при вопросах или на практике.

## Демонстрации

- `#unit-lab`: запустить ошибочную версию, спросить почему пустота превратилась в 0; включить исправление, повторить. Реальные вызовы в браузере, **не Jest**.
- `#component-lab`: пустое поле → отказ; корректный ввод → успех; включённый отказ → сообщение, ввод остаётся; повтор → успех. Локальный callback, не настоящий HTTP.
- `shop/`: добавить книгу и поменять цену; увидеть изменение итоговой суммы. Reload сбрасывает локальные данные, это честно подписано.

## Вопросы аудитории

- Какую проблему вы лично получили бы от неверной цены / записи / потерянного текста?
- Что доказывает зелёный тест, а что остаётся неизвестным?
- Почему правильная функция не гарантирует подключённую кнопку?
- Чем «показали сохранение» отличается от «данные действительно сохранились»?
- Почему disabled не гарантирует отсутствие повторной серверной операции?
- Как сломать ваш сценарий так, чтобы тест это заметил?
