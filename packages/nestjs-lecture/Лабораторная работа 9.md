# Лабораторная работа 9

## NestJS и база данных

**Срок сдачи: с 24 ноября по 2 декабря 2026 года включительно.**

### Вводные

Продолжите свой проект из работы №8, не переписывая фронтенд. Выберите одну сущность своего приложения и одно изменяемое поле: например, книгу и её цену.

### Варианты архитектуры

- React → NestJS → БД. Контроллер принимает запрос, сервис отвечает за операцию и обращается к слою хранения. Можно использовать MongoDB, как в лекции.
- React → NestJS → Java API → БД. NestJS служит прослойкой для фронтенда (BFF): принимает запрос, вызывает Java API и возвращает клиенту результат. Данными владеет Java-бэкенд. Вторая БД и прямой доступ из NestJS к таблицам Java **не нужны**.

Выберите **один** вариант. Критерий общий: в проверяемом сценарии браузер обращается к NestJS, а данные приходят из настоящей базы. Для защиты используйте локальную или учебную БД и тестовую запись.

## Критерии оценок

Каждый следующий уровень включает требования предыдущего.

### Удовлетворительно

Создайте модуль NestJS и реализуйте GET-запросы для чтения из БД: список записей и запись по идентификатору. Покажите данные в интерфейсе. Запись в базу на этом уровне не требуется.

### Хорошо

Реализуйте все три операции для одной сущности:

- POST создаёт запись.
- PUT полностью заменяет редактируемые данные записи.
- PATCH изменяет только переданные поля, сохраняя остальные.

После каждой операции выполните GET и покажите, что результат сохранён в БД.

### Отлично

- HTTP 400: отклоните некорректный запрос и поясните, что исправить. Например: «Цена не может быть отрицательной».
- HTTP 500: обработайте внутренний сбой и поясните, какая операция не удалась. Например: «Не удалось сохранить книгу из-за внутренней ошибки». Не возвращайте клиенту стек вызовов или реквизиты подключения.

На защите покажите статус и сообщение в ответе API в обоих случаях. Для проверки 500 воспроизведите контролируемый сбой сервиса в учебной среде.
