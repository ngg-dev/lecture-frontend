# Лабораторная работа 9. NestJS и база данных

Продолжите свой проект из работы №8, не переписывая фронтенд. Выберите одну сущность своего приложения и одно изменяемое поле: например, книгу и её цену. Срок назначает преподаватель.

**Два равноправных варианта на любую оценку:**

- React → NestJS → БД. Контроллер принимает запрос, сервис отвечает за операцию и обращается к слою хранения. Можно использовать MongoDB, как в лекции.
- React → NestJS → Java API → БД. NestJS служит прослойкой для фронтенда (BFF): принимает запрос, вызывает Java API и возвращает клиенту результат. Данными владеет Java-бэкенд. Вторая БД и прямой доступ из NestJS к таблицам Java **не нужны**.

Выберите **один** вариант. Критерий общий: в проверяемом сценарии браузер обращается к NestJS, а данные приходят из настоящей базы. Для защиты используйте локальную или учебную БД и тестовую запись.

## Удовлетворительно — 3: прочитать данные

- Оформите модуль NestJS, контроллер с GET-маршрутом списка и сервис. В первом варианте сервис получает записи из БД, во втором — через Java API, который читает БД.
- Покажите список в своём React-интерфейсе. На защите добавьте запись с узнаваемым названием в учебную БД или через существующий серверный инструмент. Обновите страницу: новая запись появилась. Писать форму добавления на «3» не требуется.
- **На защите:** покажите адрес запроса в Network, маршрут контроллера и место чтения из БД. Вопрос: кто в вашей схеме владеет данными?

## Хорошо — 4: сохранить изменение

- Выполните всё на «3». Добавьте в интерфейс изменение одного поля. Например, сохраните цену 750 вместо 690. Отправьте PATCH или PUT в NestJS; в варианте BFF передайте изменение в Java API и дождитесь его результата.
- Успех показывайте только после подтверждения сервера. Перезапустите серверные приложения, не очищая БД, и снова откройте страницу. Новый GET должен вернуть сохранённое значение.
- **На защите:** покажите запрос на запись и отдельный GET после перезапуска. Вопрос: почему изменённое число на экране сразу после клика ещё не доказывает запись в БД?

## Отлично — 5: правильно обработать отказ

- Выполните всё на «4». Задайте правило поля (например, цена — конечное неотрицательное число). Отправьте некорректное значение прямо в NestJS API: ожидается HTTP 400. Для корректного запроса к отсутствующей записи ожидается 404. Валидация может выполняться в NestJS или Java, но наружу NestJS должен вернуть осмысленный статус, а не 200 с текстом ошибки.
- Покажите отказ при сохранении из интерфейса: например, откройте карточку, удалите учебную запись через инструмент БД и попробуйте сохранить изменение. Форма показывает ошибку, не сообщает об успехе и позволяет повторить действие. Для проверки повтора восстановите запись с тем же id и сохраните снова.
- **На защите:** после ответа 400 повторите GET существующей записи и покажите, что значение не испорчено. Объясните путь ошибки от сервера до формы.

## Что сдать и как проверить

Сдайте ссылку на код и README: схема выбранного варианта, команды запуска БД и приложений, способ создать тестовую запись, адреса GET и PATCH/PUT. Укажите названия переменных окружения, но не пароли. Сохраните проверки предыдущей работы.

Проверяющий запускает проект по README. Пример ручной проверки для книги (замените адрес и id на свои):

```sh
curl -i http://localhost:3000/books
curl -i -X PATCH http://localhost:3000/books/demo -H 'Content-Type: application/json' -d '{"price":750}'
curl -i http://localhost:3000/books/demo
```

Если отдельного GET по id нет, проверьте запись в GET списка. Для уровня «5» повторите PATCH с ценой −1, затем с допустимой ценой и несуществующим id. Проверьте статус и содержимое БД, а не только снимок интерфейса.

**Не засчитывается:** массив вместо БД, localStorage, JSON-файл или mock вместо рабочего серверного пути; прямой вызов Java из React в демонстрируемом сценарии; подмена ошибки успешным ответом. Моки допустимы в тестах, но не заменяют защиту с БД. Docker, отдельный микросервис и новый стек хранения не обязательны.

**Опора в лекции:** на «3» — «Путь запроса от React к сервису», «Как данные организованы в MongoDB», «Backend for Frontend»; на «4» — «Как сервис выполняет операцию» и рабочий пример изменения цены из README; на «5» — блок об ошибках API и состояниях интерфейса.
